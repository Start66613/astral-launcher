# P0-1：任务取消与持久化（已完成）

> 对应 `03-契约提案与任务拆分.md` 的 P0-1。提交：`feat(core): 任务取消与跨重启持久化`。

---

## 1. 改了什么

### 1.1 Task 新增两个字段（增量，不破坏现有前端）

```ts
interface Task {
  // …原有字段不变…
  bootId: string;      // 产出该任务的进程启动标识
  cancelling: boolean; // 已请求取消，等待 worker 停下
}
```

`mergeTask` 的 revision/终态规则不需要改。前端可以：
- `cancelling === true` → 按钮显示"正在取消…"并禁用；
- `state === "error" && error.code === "INTERRUPTED"` → 上次启动器退出时没跑完。

### 1.2 取消变成真流程

旧实现：`cancel_task` 直接把状态改成 `cancelled`，后台线程照样下载、照样写盘。

新实现三步：

```
cancel_task(id)  →  accepted: true, cancelling: true, 令牌置位
worker 在阶段边界检查 task::check_cancel(id)
worker 确认停止 → task::cancelled(id) → state: "cancelled"
```

- 失败/完成之后 ignore（终态粘滞）。
- 没有令牌的历史任务（重启前留下的）直接收尾，避免永远卡在"正在取消"。

### 1.3 任务落盘 + 重启对账

- 位置：`%APPDATA%\Astral\tasks.json`（可用 `ASTRAL_DATA_DIR` 覆盖，测试用）。
- 写入方式：先写 `tasks.json.part` 再 `rename`——和下载同样的原子替换，避免半截 JSON。
- 启动时：载入历史任务，**把上次的 `queued` / `running` / `cancelling` 一律改成
  `error` + `error.code = "INTERRUPTED"`**，`revision + 1`。
- 任务 id 改成 `task_<毫秒时间戳>_<序号>`，跨进程不重复（原来是纯序号，重启后会撞）。

## 2. 诚实的能力边界

| 场景 | 现在能不能立刻停 |
|---|---|
| 我们的 `download_to` | 阶段边界停；**单个文件传到一半不能中断**（portablemc 的下载循环没有取消钩子） |
| `start_install`（原版安装） | 阶段边界停；已下载完的文件保留（下次复用），不删 |
| `start_install_loader` | 同上 |
| `start_create_instance` | 只是建目录，瞬间完成，取消意义不大 |
| `start_launch` | 进程起来后属于 `GameSession`，取消任务不影响已启动的游戏 |

**这一轮没有实现"单文件传输中断"**，因为要自己写 reqwest 流式循环替换 portablemc 的下载器；已在 `03` 号文档里列为后续项。现在的保证是：取消后**不会再开始新文件**，也不会把半截文件当成成品（`.part` 机制）。

## 3. 验证

`--selftest` 从 31 项扩到 **36 项，全过**，新增：

```
PASS task boot id          新任务带 bootId
PASS task cancel accepted  受理后 cancelling=true 且令牌置位
PASS task cancel terminal  worker 确认后 state=cancelled，cancelling=false
PASS task cancel sticky    终态后迟到的 progress 不会改回来
PASS task persisted        tasks.json 真实落盘
```

自检写的是临时目录（`ASTRAL_DATA_DIR`），不污染你的 `%APPDATA%\Astral`。

## 4. 对前端的建议

1. 取消按钮可以开放了，但文案分两段：点击后显示"正在取消…"（`cancelling`），
   收到 `state === "cancelled"` 才算真的停了。
2. 启动器重开后，看到 `INTERRUPTED` 的任务不要显示成"失败"，显示成
   "上次退出时未完成"，并提供重新执行入口。
3. 任务列表可以按 `bootId` 分组，把"本次会话"和"历史"分开。
