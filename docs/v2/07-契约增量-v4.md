# 契约增量 v4（V2 后端第一批）

> 相对 `docs/api-contract.md` v3.3。全部是**增量**：已有命令签名不变，
> 新字段都带默认值，旧前端不会崩。

---

## 1. 新增命令

| 命令 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `list_loader_builds` | `gameVersion, kind` | `LoaderBuild[]` | 四类加载器的**全部**构建 |
| `list_target_worlds` | `instanceId` | `WorldTarget[]` | 存档稳定 ID，数据包安装用 |

### LoaderBuild

```ts
interface LoaderBuild {
  id: string;              // "fabric-0.16.9"
  kind: "fabric" | "quilt" | "forge" | "neoforge";
  version: string;         // 已剥掉 MC 前缀（forge）
  mcVersion: string;
  stability: "stable" | "beta" | "alpha" | "unknown";
  recommended: boolean;
  publishedAt: string | null;   // 三家数据源都不给发布时间
  available: boolean;
  unavailableReason: string | null;
}
```

- 查到但无适配 → 返回 `[]`；网络/解析失败 → 抛 `NETWORK`。**两者不要混**。
- `kind` 传未知值 → `UNSUPPORTED`。
- Fabric/Quilt 可安装；**Forge/NeoForge 目前只能列、不能装**，UI 需相应禁用。

### WorldTarget

```ts
interface WorldTarget {
  worldId: string;        // w_<8 hex>，由目录名派生，稳定
  displayName: string;    // 目录名，仅供显示
  dir: string;
  lastModified: string;
  sizeBytes: number;
  gameVersion: string | null;   // 未解析 level.dat，恒 null
}
```

- 前端只能用 `worldId` 回传给安装接口，**不要用 displayName 拼路径**。
- 不存在的 `worldId` 会被拒绝，不会回退到全局目录。

## 2. Task 字段增量

```ts
interface Task {
  // …v3 字段不变…
  bootId: string;       // 产出该任务的进程启动标识
  cancelling: boolean;  // 已请求取消，等 worker 停下
}
```

- `cancel_task` 返回 `{ accepted }`；`cancelling=true` 只代表**受理**，
  `state="cancelled"` 才是真的停了。
- 取消来得太晚、活儿已干完 → 任务以 `done` 结束，`result.cancelledLate = true`。
- 启动器重启后，上次未结束的任务变 `state="error"`、`error.code="INTERRUPTED"`。
- 后台线程 panic 会被捕获，任务以 `INTERNAL` 失败，不会永远 `running`。

## 3. Session 字段增量

```ts
interface GameSession {
  // …v3 字段不变…
  reconciled: boolean;  // 重启后按 pid 对账收尾，退出码与时长不精确
}
```

`astral://game-exit` 载荷增量：

```ts
{ …, exitKnown: boolean, crashed: boolean, reconciled: boolean }
```

- `crashed` **只在退出码已知且非 0** 时为 true；`exitCode === null` 表示未知，
  此时 `exitKnown=false`，界面应显示"已结束，退出码未知"而不是崩溃。

## 4. 新增/收紧的错误码

| 码 | 场景 |
|---|---|
| `BLOCKED_URL` | 下载地址不在白名单 / 非 https / 含 userinfo / 内网地址 |
| `HASH_MISMATCH` | 下载后校验不符，`.part` 已清理 |
| `INVALID_PATH` | 目标越出允许目录 |
| `INSTANCE_EXISTS` | 创建实例时同 id 已存在，拒绝覆盖 |
| `INTERRUPTED` | 上次启动器退出时任务未结束 |
| `CANCELLED` | 任务被取消 |

## 5. 行为变更（前端需要知道）

1. **离线 UUID 变了**：改用标准的 `MD5("OfflinePlayer:<name>")`。
   已有存档若存在旧 UUID 的 `playerdata/<uuid>.dat`，该实例会继续沿用旧身份；
   **新实例/新存档使用新 UUID**。没有自动迁移。
2. **用户名必须是 3–16 位 ASCII 字母/数字/下划线**，否则 `set_config` 与
   `start_launch` 都会返回 `INVALID_NAME`。
3. `instance.json`、`config.json`、`tasks.json` 都改成原子写；
   `config.json.bak` 会在覆盖前生成。
4. 加载器安装后如果元数据写不进去，任务会失败（以前会假装成功）。

## 7. 安装计划（v4 新增）

```ts
interface GameInstallRequest {
  name: string;
  gameVersion: string;
  loader?: { kind: "fabric" | "quilt" | "forge" | "neoforge"; version: string } | null;
  memoryMb?: number;
}

interface GameInstallPlan {
  planId: string;
  revision: number;
  expiresAt: string;          // 15 分钟
  request: GameInstallRequest;
  target: { proposedInstanceId: string; displayPath: string; isolated: true };
  files: PlannedFile[];       // 目前只列"要装的东西"，明细后续补
  issues: PlanIssue[];        // blocking=true 时禁止执行
  downloadBytes: number | null;  // 未知返回 null
}

// prepare_game_install({ request }): GameInstallPlan
// start_game_install({ planId, revision }): Task   // result: { kind:"game-install", instance }
```

规则：

- `prepare` **无副作用**：不建目录、不下载、不改配置。
- 计划一次性：`start` 取走后即失效；`revision` 不匹配或过期都返回 `PLAN_EXPIRED`。
- `issues` 里 `blocking=true` 的项会阻止执行；目前会阻塞的有：
  实例名非法、官方清单里没有该版本、Forge/NeoForge（安装未实现）、内存越界、网络不可用。
- 执行顺序：补版本文件 → 建实例 → 装加载器 → 健康检查。
  任何一步失败都会**删除本次新建的实例目录**回滚，不会留下半成品。
- 健康检查不通过 → `VERIFY_FAILED`，同样回滚。
- 取消会在步骤边界生效；已完成的步骤不回滚已下载的版本文件（那是共享资源，可复用）。

## 8. Forge / NeoForge 安装（已实现，实测通过）

start_install_loader 与 start_game_install 对 orge / 
eoforge 改用官方安装器：

1. 从 maven 下载 installer jar 到 `<gameDir>/.astral/installers/`（白名单内）；
2. 确保目标目录有 `launcher_profiles.json`（安装器硬性要求，缺了会直接退出）；
3. 用找到的 Java 执行 `--installClient <gameDir>`；
4. 对比安装前后 `versions/` 差集，取新生成的版本 id（优先名字含加载器的那个）；
5. 把该 id 写进实例的 `launchVersion`，启动时直接启动它，不再走 Fabric 装配。

Java 查找顺序：`JAVA_HOME` → `<gameDir>/jvm/*/bin/java.exe` → PATH。

**实测**：1.20.1 + Forge 47.2.0，在隔离目录 `D:\Astral\forge-test` 完成真实安装，
生成 `versions/1.20.1-forge-47.2.0`（inheritsFrom 1.20.1，
mainClass=cpw.mods.bootstraplauncher.BootstrapLauncher），下载 82 个库、81.7 MB。

**未验证**：NeoForge 实装（代码路径与 Forge 相同，但未跑过真实安装）；
Forge 版本的**启动**需要先补齐 assets，本轮未做。
### 实测补充：Forge 1.20.1 启动

同一隔离目录继续真实启动 `1.20.1-forge-47.2.0`：

- 进程存活超过 60 秒（测试脚本随后主动 kill）
- `logs/latest.log` 出现渲染线程创建纹理图集、加载着色器，说明已进主菜单
- 因此 Forge 的「安装 → 启动」链路是通的

**踩到的坑（已修正判断）**：首次启动时 `piston-meta.mojang.com` 的 assets 索引
出现过一次 TLS handshake EOF。事后复测：**直连连续三次均 200**，说明是偶发网络抖动，
不是被墙，也不是代码问题。

结论与待办：
- 下载层需要**失败重试**（当前 portablemc 内部重试不足，一次抖动就会让启动失败）。
- 现有 BMCLAPI 改写覆盖 `libraries.minecraft.net` / `resources.download.minecraft.net`
  / 版本清单，未覆盖 assets 索引与客户端 jar；属于优化项，不是阻塞项。
### 实测补充：NeoForge 1.21.1

隔离目录 `D:\Astral\neo-test`（只放了 1.21.1 的 json+jar）完整安装成功，
生成 `versions/neoforge-21.1.72`。

期间踩到三个坑，都已修：

1. **Java 安装器不读 `HTTP(S)_PROXY` 环境变量**：必须显式传
   `-Dhttp.proxyHost/-Dhttp.proxyPort/-Dhttps...`，且**必须放在 `-jar` 之前**，
   否则会被 joptsimple 当成安装器自己的参数报错。
2. **首次安装可能因个别库下载失败而整体失败**：安装器可重入（已下载的库会跳过），
   所以现在失败后自动重试一次。
3. **失败会留下半成品版本目录**：现在失败时会把本次新建的版本目录删掉。

另外给 vendored 下载器补了**连接阶段重试**（TLS 握手 EOF 这类抖动，
最多 3 次，间隔 400/800/1200ms），之前的重试只覆盖读取阶段的超时/解码错误。

## 9. 资源查询与定向安装（v4 新增，已实测）

``ts
// get_resource_project({ projectId }): ResourceProject
// list_resource_files({ projectId, gameVersion?, loader? }): ResourceFile[]
// prepare_resource_install({ request }): ResourcePlan
// start_resource_install({ planId, revision }): Task
interface ResourceInstallRequest {
  instanceId: string;
  kind: "mod" | "resourcepack" | "shaderpack" | "datapack";
  projectId: string;
  versionId: string;
  worldId?: string;    // datapack 必填
  overwrite?: boolean; // 默认 false，同名文件会被拒绝
}
``

目标目录由 Rust 解析，前端不传路径：

| kind | 目录 |
|---|---|
| mod | `instance/dirs.mods` |
| resourcepack | `instance/dirs.resourcepacks` |
| shaderpack | `instance/dirs.shaderpacks` |
| datapack | `saves/<worldId>/datapacks` |

规则：

- 只取每个版本的 primary 文件；sha1/sha512 来自 Modrinth。
- 兼容性：mod/datapack 检查 `game_versions` 与 `loaders`；不兼容报 `INCOMPATIBLE`（blocking）。
- 同名文件已存在且未显式 `overwrite` → `FILE_EXISTS`（blocking），计划里给出 `replaces`。
- 下载走白名单 + `.part` 原子替换 + SHA1/SHA512 双校验，不符删除并报 `HASH_MISMATCH`。
- 计划 15 分钟过期、一次性、revision 校验。

**实测**：隔离目录 `D:\Astral\res-test` 建了 Fabric 1.20.1 实例，
从 Modrinth 安装 Sodium（`AANobbMI`）成功：
`instances/inst_5cd90984/mods/sodium-fabric-0.5.13+mc1.20.1.jar`（948.8 KB）。

## 10. CSP 收紧（已配置，视觉验证待做）

`app/src-tauri/tauri.conf.json` 的 `security.csp` 从 `null` 改为：

``
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: https://cdn.modrinth.com https://cdn-raw.modrinth.com;
font-src 'self' data:;
connect-src 'self' ipc: http://ipc.localhost https://api.modrinth.com https://cdn.modrinth.com;
object-src 'none'; base-uri 'self'; frame-src 'none'; form-action 'none'
``

要点：
- Tauri 2 在 Windows 上需要 `ipc:` 与 `http://ipc.localhost` 才能通信。
- `style-src 'unsafe-inline'` 是 Vite/React 内联样式的现实妥协。
- 只放行 Modrinth 的图片与 API；其他远程域名一律拒绝。

**验证状态**：构建通过；因本机窗口焦点被其他程序抢占，
无法稳定截取自绘窗口，**视觉验证未完成**。合并出原生包时需要确认：
Modrinth 图标能否显示、页面是否白屏。若白屏，优先检查是否还有未放行的域名。
### 依赖解析（同一提交）

`prepare_resource_install` 现在会解析 **required 依赖**并写进计划：

- 每个依赖按其 `version_id` 或（未指定时）按实例的 MC 版本 + 加载器挑选第一个兼容文件；
- 目标目录里已有同名文件则视为已安装，跳过；
- 最多展开 10 个依赖，去重按文件名；
- 找不到兼容版本 → `DEPENDENCY_CONFLICT`（blocking），**不会静默忽略**；
- `execute` 先装依赖再装本体，每个文件都做 SHA1/SHA512 校验。

计划新增 `dependencies: PlannedDep[]`，`downloadBytes` 含依赖总量。

**实测**：在 `D:\Astral\res-test2` 的 Fabric 1.20.1 实例安装 Iris
（`YL57xq9U`），自动补装了它的必需依赖 Sodium：

``

mods/sodium-fabric-0.5.12-beta.2+mc1.20.1.jar     948.6 KB
``

> 注意：依赖只会取"第一个兼容版本"，可能与主 mod 期望的版本不同；
> 完整版本约束匹配（semver）未实现，列为后续项。

## 11. 日志与诊断预览（v4 新增）

`	s
// list_logs({ instanceId }): LogFile[]
// read_log({ instanceId, logId, limit? }): LogText
// prepare_diagnosis({ instanceId, logIds, maxLines? }): DiagnosisPreview
interface LogFile { id: string; name: string; kind: "game"|"crash"; sizeBytes: number; modifiedAt: string }
interface LogText { id: string; name: string; text: string; lines: number; truncated: boolean }
interface DiagnosisPreview { text: string; redactions: number; bytes: number; truncated: boolean; warnings: string[] }
`

规则：

- 只读 `logs/*.log` 与 `crash-reports/*.txt`；`.gz` 暂不解析。
- 日志 id 由相对路径哈希派生，**不接受前端传路径**。
- 单文件超过 4 MiB 只读尾部 4 MiB；`limit` 默认 400 行，最大 2000。
- `prepare_diagnosis` **只在本机脱敏并返回预览**，不联网、不上传；
  是否上传由界面在用户确认后决定。
- 脱敏内容：`access_token` / `Authorization` / `client_secret` 等键值（保留键名）、
  邮箱、Windows 用户目录（`\Users\<name>`）、IPv4。

**未实现**：真正的 AI 分析（`start_diagnose`）——需要用户提供 DeepSeek API Key，
且必须先有"用户确认上传"的界面流程；本轮只做本地预览。

**验证**：--selftest 新增 5 项（列出、id 稳定、尾部截断、未知 id 拒绝、脱敏命中）。

## 12. 整合包 .mrpack（v4 新增，已实测）

``ts
// prepare_modpack_install({ projectId, versionId, name?, memoryMb? }): ModpackPlan
// start_modpack_install({ planId, revision }): Task   // result: { kind:"modpack", instance }
interface ModpackPlan {
  planId: string; revision: number; expiresAt: string;
  info: { name; summary; versionName; mcVersion;
          loaderKind: string|null; loaderVersion: string|null;
          fileCount: number; totalBytes: number };
  issues: PlanIssue[];
  downloadBytes: number;
}
``

流程：

1. 取 Modrinth 版本信息 → 下载 `.mrpack` 到 `<gameDir>/.astral/modpacks/`（白名单）；
2. 解析 `modrinth.index.json`：MC 版本、加载器（fabric/quilt/forge/neoforge）、文件清单；
3. 规划阶段校验每个路径（**拒绝绝对路径、`..`、盘符、反斜杠**）与下载来源白名单；
4. 执行：建实例 → 补游戏本体 → 装加载器 → 按 index 下载文件（逐个 SHA1 校验）
   → 解压 `overrides/` 与 `client-overrides/` → 健康检查；
5. 任一步失败：**删除本次新建的实例目录**，不留半成品。

安全限制：单个 index ≤ 8 MiB；解压总量 ≤ 512 MiB（防压缩炸弹）；
解压前逐条 `canonicalize` 校验仍在实例目录内（防 zip-slip）。

**实测**：`D:\Astral\forge-test` 安装 Spunky Optimized（`22jj8tHD`）：

``
实例 inst_f73f1cc8 · Spunky Optimized · 1.20.1 · fabric 0.16.10
mods 25 个文件，config 25 个文件（来自 overrides）
``

**未做**：整合包导出、依赖冲突的版本约束匹配（仍取第一个兼容版本）。

## 13. Java 探测（v4 新增）

``ts
// list_java_runtimes({ instanceId? }): JavaReport
interface JavaRuntime { path: string; version: string; major: number;
                       vendor: string; bits: number|null;
                       source: "java_home"|"game_jvm"|"common_dir"|"path" }
interface JavaReport { runtimes: JavaRuntime[];
                       requiredMajor: number|null; recommended: string|null }
``

- 扫描来源：`JAVA_HOME` → `<gameDir>/jvm/*` → 常见安装目录（Java / Adoptium /
  Microsoft / Zulu / Corretto / BellSoft） → PATH。
- 每个候选都实际执行 `java -version`，解析主版本（`1.8.0_402` → 8）。
- `requiredMajor` 读实例版本 JSON 的 `javaVersion.majorVersion`。
- `recommended` 取**主版本相等**的运行时；没有则取**大于需求里最小的那个**；
  都不满足则为 null（界面应提示"需要 Java N"）。

**未做**：自动下载/解压 JDK（目前依赖 portablemc 在启动时按需下载 Mojang JRE）；
注册表扫描（只扫目录，可能与实际安装位置有出入）。

**验证**：--selftest 新增 2 项（版本解析、挑选策略）。

## 14. 光影支持组件（v4 新增，已实测）

``ts
// get_component_catalog({ gameVersion, loader? }): ComponentCatalog
interface ComponentBuild {
  id: "iris"|"oculus"|"optifine"; label: string;
  projectId: string; requiredLoader: string|null;
  version: string|null; fileName: string|null; publishedAt: string|null;
  stability: "release"|"beta"|"alpha"|"unknown";
  recommended: boolean; available: boolean; unavailableReason: string|null;
}
interface ComponentCatalog { shaderSupport: ComponentBuild[]; fetchedAt: string }
``

| 组件 | Modrinth | 适用加载器 |
|---|---|---|
| Iris Shaders | `YL57xq9U` | Fabric / Quilt |
| Oculus | `GchcoXML` | Forge |
| OptiFine | — | **永不自动安装**（无公开 API + 分发条款限制） |

规则：

- 加载器不匹配 → `available=false` 并给出"需要 X，当前是 Y"；
- 拉到列表但该 MC 版本无适配 → `available=false` 并说明；
- 网络失败 → `available=false`，原因取错误消息；
- `recommended` 取第一个 release 渠道，没有则取第一个；
- **组件本身不在这里安装**：可用后用 `prepare_resource_install` 以
  `kind="mod"` 安装即可（或随游戏安装计划一并处理）。

**实测**（1.20.1 + fabric）：

`
iris      available=true  version=1.7.6+1.20.1
oculus    available=false 需要 forge，当前实例是 fabric
optifine  available=false OptiFine 没有公开 API，分发条款也不允许自动下载
`

**未做**：Oculus 在 NeoForge 上的可用性（上游只出 Forge 版）；
组件与光影包的兼容性检查（光影包是资源包，不走这里）。
### 实测补充：NeoForge 1.21.1 启动

隔离目录 `D:\Astral\neo-test` 启动 `neoforge-21.1.72` 成功：

- 进程存活超过 60 秒（脚本随后 kill）；
- `logs/latest.log` 显示 `ModLauncher 11.0.4 starting`、
  NeoForge `AnimationLoader` 加载完成、渲染线程建纹理图集 → 已进主菜单。

**两个附带发现**：

1. 日志里是 `java version 21.0.7 by Microsoft`——本机系统 PATH 只有 Java 25，

## 15. 模组更新检查（v4 新增，已实测）

``ts
// check_mod_updates({ instanceId, limit? }): UpdateReport
interface ModUpdate { fileName: string; projectId: string;
                      currentVersion: string; latestVersion: string;
                      latestVersionId: string; latestFileName: string }
interface UpdateReport { checked: number; unknown: number;
                         updates: ModUpdate[]; skipped: number }
``

流程（全只读）：

1. 对 `mods/*.jar` 逐个算 SHA1；
2. `GET /v2/version_file/{sha1}` 反查项目与当前版本；
3. `GET /v2/project/{id}/version?game_versions=[…]&loaders=[…]` 取该实例版本下最新兼容文件；
4. 版本 id 不同才报更新。

`limit` 默认 20，最多 200；超出的计入 `skipped`。
非 Modrinth 来源或已下架的 jar 计入 `unknown`，不会被误报成"有更新"。

**实测**（res-test2 实例，2 个 mod）：

``
checked=2 unknown=0 updates=1
sodium-fabric-0.5.12-beta.2+mc1.20.1.jar  mc1.20.1-0.5.12-beta.2-fabric -> mc1.20.1-0.5.13-fabric
``

**未做**：一键更新（需要"删旧 + 装新"的原子流程，避免更新失败后两边都不在）。
### 一键更新（原子替换，已实测）

``ts
// start_mod_update({ instanceId, fileName, projectId, versionId }): Task
// result: { kind: "mod-update", file: 新文件名, removed: 旧文件名 }
``

顺序（**先新后旧**）：

1. 校验旧文件确实存在（否则报 `INVALID_PATH`，不凭空多一个文件）；
2. 确认目标版本的 `project_id` 与请求一致，防止装错项目；
3. 下载新文件到 `.part`，SHA1 校验后再替换；
4. 有 SHA512 就再校一遍，不符则删新文件并保留旧文件；
5. **新文件确认落盘后才删除旧文件**；同名发布视为原地替换，不删。

任一步失败：旧文件一定还在，实例不会变成"两边都没有"。

**实测**（res-test2 实例）：

``

LIVE update-apply ok:    sodium-fabric-0.5.12-beta.2+mc1.20.1.jar -> sodium-fabric-0.5.13+mc1.20.1.jar

mods/iris-1.7.6+mc1.20.1.jar              （未受影响）
mods/sodium-fabric-0.5.13+mc1.20.1.jar    （旧的 0.5.12 已删除）
``

## 18. 任务重试（v4 补充）

``ts
// retry_task({ taskId }): Task
``

规则：

- 只有 **error / cancelled** 的任务可以重试；运行中或已完成会被拒绝；
- 任务必须记录了发起参数（`retrySpec`），否则返回 `UNSUPPORTED`；
- 新任务的 `retryOf` 指向原任务，`Task.retrySpec` 同样保留，可链式重试；
- 目前支持 **install** 与 **mod-update** 两类；
  其余（安装计划、资源、整合包、加载器）需要重新规划，返回
  `UNSUPPORTED|该任务需要重新规划，请从界面重新发起`。

为什么只有两类：这两类的参数是自足的（游戏版本 / 实例+文件+项目+版本）。
计划类任务的 `planId` 一次性且 15 分钟过期，重试必须重新 `prepare`，
否则等于用一个失效计划执行。

**验证**：--selftest 新增 4 项（运行中拒绝、缺参数拒绝、未知类型拒绝、已知类型通过）。

## 19. JDK 自动下载（v4 新增，已实测）

``ts
// install_java({ major }): Task
// result: { kind: "install-java", major, version, path }
``

流程：

1. `GET api.adoptium.net/v3/assets/latest/{major}/hotspot`（x64 / jdk / windows / eclipse）；
2. 下载 zip 到 `<gameDir>/.astral/jdk/`，用 API 给的 **SHA256** 校验，不符即删；
3. 解压到 `<gameDir>/jvm/adoptium-{major}/`，逐条校验路径（防 zip-slip），总量上限 2 GiB；
4. 找到 `bin/java.exe` 并返回路径。

安全说明：

- 白名单新增 `api.adoptium.net` 与 `github.com`；
  GitHub 用于 release 重定向，URL 由 API 返回而非用户输入，且下载后有 SHA256 兜底。
- 不修改系统环境变量、不写注册表，只落在游戏目录内。

**实测**（隔离目录 `D:\Astral\jdk-test`，Java 17）：

``
LIVE jdk ok:   version=17.0.20+101

               bytes=190817615
LIVE jdk runs: openjdk version "17.0.20.1" 2026-08-18
``

**未做**：JDK 升级/清理（旧版本会留在 jvm 目录）、ARM64 与 Linux/macOS 参数（当前固定 x64 + windows）。
### Java 收尾（同轮）

1. **修了扫描漏检**：自己下载的 JDK 解压在 `jvm/adoptium-<major>/<jdk 目录>/bin/java.exe`，
   比原生 JRE 多一层目录，原来的扫描会漏掉。现在两层都找。
   实测：`LIVE java found 1 runtimes · java 17.0.20.1 (major 17)`。
2. **新增 `list_managed_jdks`**（只读）：列出本项目下载过的 JDK ——

删除 JDK 目录属于不可逆操作，本轮**没有**提供删除命令；

## 20. 启动阶段：稳定的 phase（v4 补充）

Task.stage 是自由字符串（会随实现变化），**不适合驱动动画**。
因此新增稳定字段：

``ts
interface Task {
  // …
  phase: "queued" | "validating" | "checking-files" | "preparing-java"
       | "downloading" | "launching" | "process-created"
       | "done" | "failed" | "cancelled";
}
``

内部 stage → phase 的映射（`task::phase_of`）：

| stage | phase |
|---|---|
| `queued` | queued |
| `validate` | alidating |
| `resolve` / `assets` / `extract` | checking-files |
| `jvm` | preparing-java |
| `download` | downloading |
| `launch` | launching |
| `spawned` | process-created |
| `done` | done（launch 任务为 `process-created`） |
| `error` | ailed |
| `cancelled` | cancelled |

启动任务现在会显式发出 `validate` 与 `spawned` 两个阶段：

- `validate`：开始检查实例与版本文件；
- `spawned`：进程已创建（此时任务随即 `done`）。

**running / exited 不在这套 phase 里**——那是 GameSession 的状态，
通过 `get_active_session` 与 `astral://game-exit` 获取。
动画不要在 `process-created` 之后自行宣布"游戏已运行"。

**验证**：--selftest 新增 3 项（映射表、progress 写入、finish 写入）。

## 23. 资源安装与实例保护（v4.1 修正）

### 23.1 任务绑定实例

start_resource_install 创建的任务现在带 instanceId，ResourcePlan 也新增
`instanceId` 字段。此前任务没有实例归属，界面无法按实例聚合、也无法做运行期保护。

### 23.2 只允许托管实例

`prepare_resource_install` 在**任何网络请求之前**先检查实例：

- `managed === false`（兼容实例，共享游戏目录）→ 直接返回
  `UNSUPPORTED|兼容实例共享游戏目录，不能安装资源`；
- 版本必须属于请求的 `projectId`，否则 `INVALID_VALUE|版本与项目不匹配`；
- 文件名必须是**单层相对名**（不能含目录、`..`、盘符），否则 `INVALID_PATH`。

### 23.3 校验时机：先校验，再提交

新增 `net::download_verified(url, dest, sha1, sha512, on)`：

1. 下载到 `<dest>.part`；
2. 在 `.part` 上校验 SHA1 与 SHA512；
3. **全部通过后才 rename 覆盖正式文件**。

以前 SHA512 是在 rename 之后校验，一旦不符只能删掉新文件——**旧文件已经被覆盖**，
回滚不回去。现在任何校验失败都只删 `.part`，旧文件原样保留。

### 23.4 实例修改保护

`update_instance` 与 `delete_instance` 一样，在实例运行中或有进行中任务时返回
`INSTANCE_BUSY`（改名会让启动/安装期间的路径漂移）。

### 23.5 session::active 语义

ctive() 现在只返回**进程存活**的会话。pid 已失效的会话会被就地标记
`exited` 并持久化，但**不再作为返回值**——此前它会把已退出的会话当成"在运行"返回，
导致 `start_launch` / `delete_instance` 误报 `INSTANCE_BUSY`。

查"上一次退出"请用 `list_sessions`（get_active_session 返回 null 时）。

**验证**：--selftest 84 项（新增 3 项：失效会话不再 active、会话被标记 exited、
兼容实例被拒绝）；真机复测三类资源安装仍通过。

## 24. 取消语义与加载器复用（v4.2 修正）

### 24.1 三类长任务都能真正停下

| 任务 | 取消检查点 |
|---|---|
| 资源安装 | 开始前、每个依赖下载前、本体下载前 |

**迟到取消**：活儿已经干完才收到取消请求时，任务如实报告 `done` 并带
`cancelledLate: true`，不会显示成"已取消"。

限制：取消发生在**文件边界**——单个大文件下载中途不会被打断（portablemc 的

### 24.2 Forge / NeoForge 重复安装与多实例共享

新增 `core::forge_version_id(kind, mc, ver)`：

- `forge` → `{mc}-forge-{ver}`
- `neoforge`（1.20.1 以外）→ `neoforge-{ver}`
- `neoforge` + 1.20.1 → `1.20.1-forge-{ver}`

安装前若该版本已存在，直接复用并返回（不重复跑安装器、不重复下载）；
安装后优先按这个 id 判定成功，**不再依赖"本次是否新增目录"**——
多个实例共享同一份加载器不会被误判为失败。

**验证**：--selftest 88 项（新增 4 项：id 推导、复用不联网、取消短路、取消不落文件）；
真机复测：对已安装目录再次执行 Forge 安装，直接返回 `1.20.1-forge-47.2.0`。

interface GameInstallRequest {

### 25.2 计划里给出组件

### 25.4 过程中发现的真缺陷

`ComponentBuild.version` 之前存的是**版本号**（`1.7.6+1.20.1`），
却在计划里被当成 version id 用，导致请求 `/v2/version/1.7.6+1.20.1` 返回 400。
现在拆成两个字段：`versionId`（安装用）与 `version`（展示用）。

**验证**：

- --selftest 89 项（新增 OptiFine 被拒绝）

## 26. 加载器兼容与依赖约束（v4.4 修正）

### 26.1 装之前先判断版本是否搭配

新增 `core::loader_compatible(kind, mc, ver)`，`installer_url` 会先调用它：

| 情况 | 结果 |
|---|---|
| Forge 版本号带了游戏前缀（`1.20.1-47.2.0`） | `INVALID_VALUE`，否则会拼出 `1.20.1-1.20.1-47.2.0` |
| Forge 版本号不是数字开头 | `INVALID_VALUE` |
| NeoForge + 1.20.1 却不是 47.1.x | `INCOMPATIBLE` |
| NeoForge 版本前缀有明确归属（20.2/20.4/20.6/21.0/21.1）但与 mc 不符 | `INCOMPATIBLE`，并说明对应版本 |
| 前缀未知 | 放行（宁可让下载给出明确错误，也不误伤新版本） |

好处：错误从"下载 404"变成"这两个版本不搭配"，且**不发网络请求**。

### 26.2 依赖解析更严

- 依赖指定了 `versionId` 时：校验它**确实属于**该 `projectId`，且与实例的游戏版本 / 加载器兼容，否则记
  `DEPENDENCY_CONFLICT`（阻塞）；
- 未指定时：兼容版本里按 `release > beta > alpha` 排序取最稳的（以前直接取第一个）；
- 同一个项目被解析出两个不同版本 → 记 `DEPENDENCY_CONFLICT`（阻塞），
  不让两个 jar 互相覆盖。

**验证**：--selftest 93 项（新增 4 项：Forge 兼容、NeoForge 兼容、前缀映射、不搭时提前拒绝）；构建 0 warning。

## 27. 光影组件版本自选（v4.5 新增）

### 27.1 查询全部兼容版本

``ts
// list_component_versions({ id, gameVersion, loader }): ComponentVersion[]
interface ComponentVersion {
  versionId: string;      // Modrinth version id（安装时用它）
  versionNumber: string;  // 展示用版本号，例如 1.7.6+1.20.1
  channel: "release" | "beta" | "alpha";
  gameVersions: string[];
  loaders: string[];
  fileName: string;       // 实际发行文件名
  size: number;
  publishedAt: string;
  recommended: boolean;   // 后端推荐（稳定渠道里最新的那个）
}
``

排序为 `release > beta > alpha`，第一个标记 `recommended`。
组件不可用时返回错误：`UNSUPPORTED`（OptiFine 无公开 API）、
`INCOMPATIBLE`（Oculus 需要 Forge 等）。

### 27.2 计划里指定版本

``ts
interface GameInstallRequest {
  // …
  shaderSupport?: "iris" | "oculus" | "optifine" | "none";
  shaderSupportVersion?: string;  // 可选：上面查到的 versionId
}
``

校验链（任一不满足即**阻塞 issue**，不会静默换成别的版本）：

1. 组件 id 已知；
2. `versionId` 确实属于该组件的 Modrinth 项目；
3. 该版本支持请求里的 Minecraft 版本；
4. 该版本支持请求里的加载器。

不传 `shaderSupportVersion` 时保持旧行为：后端挑推荐版本。

### 27.3 三个概念不要混

| 字段 | 含义 | 例子 |
|---|---|---|
| `versionId` | Modrinth 版本主键，**安装必须用这个** | `1CMVXDHo` |
| `versionNumber` | 人看的版本号 | `1.7.2+1.20.1` |
| `fileName` | 实际下载的文件名 | `iris-1.7.2+mc1.20.1.jar` |

早期把 `versionNumber` 当 `versionId` 用，导致 `/v2/version/1.7.6+1.20.1` 返回 400，
已在本轮拆开。

**真机验证**：

``
list_component_versions(iris, 1.20.1, fabric) → 13 个版本，推荐 s5eFLITc / 1.7.6
选推荐版本 s5eFLITc → 装出 iris-1.7.6+mc1.20.1.jar
选非推荐 1CMVXDHo（1.7.2）→ 装出 iris-1.7.2+mc1.20.1.jar + 依赖 sodium
越权版本 NotARealVersionId → 被拒绝
``

## 28. 旧下载接口 download_to 安全加固（v4.6）

### 28.1 复核发现的问题

| 问题 | 原状 |
|---|---|
| 全局目录写入 | 不传 instanceId 时 Mod 直接落到共享 `mods/` |
| 静默覆盖 | 目标存在时直接覆盖，无提示 |
| 无校验 | `download_atomic` 传 `None`，不做哈希 |
| 路径校验不完整 | 只校验在游戏目录内，未校验在实例目录内 |
| 来源 | 已有白名单（初始 URL） |
| 重定向 | 由底层下载器跟随，白名单管不到跳转目标 |

### 28.2 现在的行为

``ts
// download_to({ url, kind, filename, instanceId?, sha1?, sha512?, overwrite? }): string
``

- `kind` 为 `mod` / `datapack` 时**必须**给 `instanceId`，否则
  `INVALID_VALUE`（并提示改用 `prepare_resource_install`）；
- 目标已存在且未传 `overwrite: true` → `FILE_EXISTS`；
- 传了 `sha1` / `sha512` 就在落盘前校验，不符则 `HASH_MISMATCH`；
- 给了实例时，路径同时校验在**实例目录**与游戏目录内。

### 28.3 弃用计划

1. 新 UI 一律走 `prepare_resource_install` + `start_resource_install`（有计划、有依赖、有校验）；
2. `download_to` 保留但视为兼容层，**只用于资源包/光影包这类全局目录**；
3. 等 Codex 确认新 UI 不再调用后，再删除该命令（删除前会先查前端调用点）。

### 28.4 仍存在的限制

重定向目标不在白名单校验范围内（下载器内部跟随）。
彻底解决需要替换下载器或改造 portablemc 的重定向策略，本轮未做，已如实记录。

**验证**：--selftest 94 项（新增 1 项目录规则）。

## 29. 依赖解析补强（v4.7）

| 情况 | 现在的处理 |
|---|---|
| 原版实例的依赖 | 只从"不声明加载器或 vanilla/minecraft"的文件里挑，避免给原版塞 Fabric 依赖 |
| 依赖文件名带目录 / `..` / 盘符 | `INVALID_PATH` 阻塞，不落盘 |
| 两个依赖同名但来自不同项目 | `DEPENDENCY_CONFLICT` 阻塞，要求人工选择 |

关于递归与循环：本版**不做递归安装**，遇到"依赖还有依赖"直接要求人工处理，

## 30. 取消语义与实例保护复核（v4.8）

### 30.1 取消的三种结果（四类任务一致）

| 情形 | 任务状态 | 结果负载 |
|---|---|---|
| 请求取消 → 确实停下 | `cancelled` | — |
| 请求取消 → 活儿已经干完 | `done` | `cancelledLate: true` |
| 没取消但失败 | `error` | 错误码 + 消息 |

四类长任务（资源安装 / 整合包 / JDK / 游戏安装）都按这个规则，资源安装与整合包
在文件边界检查，JDK 在下载与解压之间检查。

### 30.2 临时文件与回滚

- 下载：任何失败或取消都只删 `.part`，正式文件不变（`download_verified`）；
- 游戏安装 / 整合包：失败或取消时**只删除本次新建的实例**（`created` 记录），
  不会动已有实例；
- 资源安装：已成功落盘的依赖保留（它们是完整文件），失败的那个文件不会半截存在。

### 30.3 实例保护复核结论

| 检查项 | 结论 |
|---|---|
| 任务绑定实例 | 资源/加载器/更新/启动在创建时绑定；游戏安装与整合包在实例建好后立即 `bind_instance` |
| 运行中实例被修改 | `update_instance` 与 `delete_instance` 均返回 `INSTANCE_BUSY` |
| 安装计划重复执行 | `plan::take` / `resources::take` 用 `map.remove`，计划一次性 |
| 删除与写入竞态 | 删除前检查存活会话与进行中任务，任务已绑定实例 |
| 意外删除用户目录 | 只删托管实例目录；默认进回收站；不触碰 `versions/` 兼容实例 |

### 30.4 仍存在的边界

- 单个大文件下载中途不可中断（只在下一次边界检查时停下）；
- 依赖不做递归安装（见 §29）；
- 重定向目标不在白名单内（见 §28）。

## 31. 加载器版本校验与 Java 自动选择（v4.9）

### 31.1 装加载器前先确认版本存在

`start_install_loader` 现在会先拉一次该游戏版本的构建列表，校验请求的版本号：

- 版本不在列表 → `INCOMPATIBLE`，并给出 3 个可用示例；
- 未知加载器类型 → `UNSUPPORTED`（原有）。

好处：以前要等安装器下载/执行到一半才 404，现在立刻给出"这个版本不存在"。

### 31.2 启动时自动选择 Java

启动任务在实例没有显式 `javaPath` 时：

1. 扫描本机 Java（`java::scan`）；
2. 从版本 JSON 读所需主版本（`required_major`，**会沿 inheritsFrom 链找**，
   因为 Forge/NeoForge 版本自己通常不带 `javaVersion`）；
3. 用 `pick_for` 选优先相等、其次更高的运行时。

显式配置的 `javaPath` 依旧优先；找不到合适的运行时则回退到 portablemc 默认逻辑。

**验证**：--selftest 95 项（新增"沿继承链读 javaVersion"）；单元测试 49 passed。
### 31.3 实现位置与真机验证

自动挑 Java 抽成 `core::auto_java_for(game_dir, version)`，启动命令与自检钩子
走同一份逻辑（不是两套）。

真机验证（Fabric 1.20.1，实例未配置 javaPath）：

``
LIVE launch java=\\?\D:\Astral\forge-test\jvm\java-runtime-gamma\bin\java.exe
LIVE launch ok: pid 65036 still running after 60s
``

即：自动挑中了游戏目录内的 Java 17（java-runtime-gamma），并成功进入主菜单。

## 32. 实例修复 repair_instance（v4.10 新增）

### 32.1 命令

``ts
// repair_instance({ instanceId }): Task
// result: { kind: "repair", instanceId, steps: string[], ok: true }
``

### 32.2 做什么

先算"缺什么"，再**只补缺失的部分**：

| 步骤 | 触发条件 | 动作 |
|---|---|---|
| `base` | 版本 json / jar / 依赖库 / 资源索引任一缺失（沿 inheritsFrom 链判断） | 重跑游戏安装（已存在的文件会跳过） |
| `loader` | 配置了加载器但加载器版本目录缺失 | Fabric/Quilt 重装加载器；Forge/NeoForge 重跑安装器（已装会复用） |

修复后重新做一次健康检查：

- 通过 → 任务 `done`，`steps` 说明补了什么；
- 仍不完整 → 任务 `error`，`VERIFY_FAILED` 并列出剩余原因。

### 32.3 安全约束

- 不删除、不覆盖用户已有文件（安装器本身只写缺失项）；
- 实例运行中或有修复任务在跑时拒绝（`INSTANCE_BUSY` / `BUSY`）；
- 只对托管实例生效。

### 32.4 验证与边界

**已验证**：修复计划的两条路径（缺 base + loader；补齐后无步骤），--selftest 97 项。

**未单独跑真机**：真实补文件走的是已实测的 `core::install` / `core::install_loader` /
`core::install_forge_like`，但没有单独构造"删掉一个库再修复"的端到端用例——
这条在文档里如实标注，不当作已验收。

## 33. 结构化日志诊断 diagnose_instance（v4.11 新增）

### 33.1 命令

``ts
// diagnose_instance({ instanceId, logId?, maxLines? }): DiagnosisReport
interface DiagnosisReport {
  logId: string;
  logName: string;
  lines: number;
  findings: Finding[];
  text: string;   // 已脱敏的原文（供"查看日志"）
}
interface Finding {
  id: string; label: string;
  severity: "error" | "warn" | "info";
  evidence: string[];  // 命中的行，最多 3 条
  hint: string;        // 给玩家的下一步建议
}
``

### 33.2 规则（确定性匹配，不联网、不上传）

| id | 判断依据 | 建议 |
|---|---|---|
| `java-version` | UnsupportedClassVersionError / requires Java | 换对应 Java 版本 |
| `missing-class` | NoClassDefFoundError / ClassNotFound / 找不到主类 | 修复实例补依赖 |
| `mod-conflict` | Duplicate mods / Incompatible mod set / already registered | 移除冲突模组 |
| `out-of-memory` | OutOfMemoryError / Java heap space | 调大内存 |
| `graphics` | GLFW error / 窗口创建失败 / OpenGL | 更新驱动、确认独显 |
| `download` | Failed to download / Checksum / 连接重置 | 检查网络与镜像 |
| `auth` | Invalid credentials / Authentication | 重新登录或配置微软应用 |

结果按 `error > warn > info` 排序，每条最多 3 行证据。

### 33.3 与 AI 分析的区别

这是**本地规则诊断**，不是 AI：不需要 Key、不联网、不出本机。
AI 分析（DeepSeek）仍未实现，缺 Key 与显式上传确认流程，不做伪造。

## 34. 整合包边界收紧（v4.12）

### 34.1 新增校验（不合法直接拒绝整个包）

| 情况 | 结果 |

- 解压覆盖目录仍有 512 MiB 上限（原有）。
